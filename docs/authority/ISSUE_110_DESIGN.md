# #110 R3 design — typed Owner resolution ledger

Baseline 9209e7414cf9666eaa3071559205527f5b2e6591. Extend current OR grant validation rather than changing v1 meaning. Current v1 has no rerun action and no supersedes; v1 fixtures/history remain byte-identical.

## Trust and integration

Add versioned Owner authority events and durable local ledger. Trusted ingestion is a local explicit Owner-approved input boundary with issuer authority reference and detached trusted verifier callback supplied by the host application; JSON actorType/source labels alone cannot authenticate events. CLI import must use a locally provisioned trusted public-key binding and verify detached signatures over canonical event bytes (Node crypto Ed25519), not accept an unsigned text instruction or arbitrary public key passed alongside the event. Key provisioning/signing is outside this implementation. Tests generate ephemeral keys solely inside isolated fixtures. Missing configured trust root/signature => HOLD. Root binding file must be owned/read-only policy and cannot be overwritten by events.

Event schema: unique eventId, typed issuer/sourceRef, schema version, issuedAt/expiresAt, exact repository/project/task/PR/worker/session/generation/input identity, allowed and prohibited typed effects, dependency gate predicates, explicit supersedes IDs and revocation target IDs. Persist original canonical payload, signature and SHA256 in append-only store; prohibit secrets in event keys; exact keys reject widening. Schema supports operational execution rerun/recovery separately from v1 git/PR/task effects.

Derive current authority by deterministic DAG over verified durable events, not arrival time. Missing references, cycles, incomparable contradictory grants, expired/revoked applicable events => HOLD. Supersession only applies to explicitly compatible subject/scope and cannot let a lower authority remove a higher restriction. For first implementation use one pinned Owner issuer only; cross-authority delegation is out of scope. Prohibitions and unmet dependencies override allowed actions; an event that supersedes broad authority does not inherit old actions. Duplicate canonical event is idempotent; same ID different bytes rejected. Restart reads and verifies whole small bounded ledger with size limits, no mutable cached authority override.

Enforcement: #109 enrolled execution preflight checks rerun/recovery effect and exact original worker/task/PR/input. Existing authorization evaluate paths gain an optional effective-ledger evidence binding; never silently replace v1 grants or enable merge. Recovery supervisor checks only explicitly configured ledger policy; unconfigured legacy supervisor behavior unchanged and marked no-authority-ledger-enforcement, not claimed compliant. Need explicit default policy/cutover scope review; no deployed automation activation. A grant for rerun does not imply conversation restore, push/review/merge/successor/cleanup.

Terminal invocation binds event fingerprint and consumed nonce durably before effect. Single-use replay consumption uses atomic exclusive receipt with input binding; crash before effect consumes authorization conservatively, resulting HOLD, not reexecution. Independently issued resolution needed after such unknown outcomes. Observational inspect consumes nothing. Existing temporal_wait/operational_auto/human_gate vocabulary remains unchanged.

## Validation and rollback

Signed fixture broad grant, narrow prohibition, rerun-only supersession; reorder/restart; duplicate ID/substituted content; expired/revoked; missing refs/cycles; incomparable conflict; fake actor; wrong trust root; wrong signature; exact session/generation/task/PR/tree substitution; replay; crash after consumption; mixed v1/vNext. Real execution fake-child integration proves denied effects never spawn. Native merge authority remains v1 and deployment held unless separately admitted cutover. Additive source rollback preserves ledger/consumption raw custody; unsupported version HOLD.

Reviewer must check whether new trust-key provisioning makes scope too broad, whether legacy-supervisor optional enforcement is an honest completion boundary, exact scope/supersession semantics and replay atomicity. Any reduction to design-only must be recorded and not called full implementation.

## Revision 1 — exact trust, precedence and atomicity

Required host verifier API authenticates canonical payload/source proof both at ingestion and every derive/replay. It returns the configured pinned Owner and source binding, not merely payload actor labels. Optional Ed25519 adapter supports externally configured public key but no key provisioning/CLI-generated trust root. Without verifier production consumers HOLD. Existing v1 only structurally validates issuer refs and remains unchanged, with no claim that prior v1 authenticates Owner.

Scopes are full exact repository/project/task/PR/worker/session/generation/input binding with no wildcard. For one pinned Owner, all applicable unsuperseded heads must yield one unambiguous effective event; multiple heads HOLD even if allegedly compatible. New resolution must explicitly supersede all conflicting previous applicable heads in exactly same scope. Ancestors remain superseded after newer event expiry/revocation, so previous broad grants cannot revive. Descendant permits do not inherit ancestors; same pinned Owner explicit supersession can remove earlier prohibition, while current head's explicit prohibition and unmet gate block its allowed action. Cyclic/missing/foreign-scope refs HOLD.

Store-wide exclusive mutation lock serializes ingestion, derive, consume and effect permit. Library callback executes the barrier permit/restore initiation while lock held after atomic durable single-use receipt; this consumption+callback ordering is the authorization linearization point. A restriction arriving afterwards affects future invocations, not revocation of already admitted sole invocation. If permit initiation throws after consumption, authorization remains consumed and requires new resolution; no automatic reuse. Lock stale after crash HOLD; no read-check-unlink reclamation.

First enforced vocabulary includes execution.run, execution.rerun and conversation.restore only. Do not route v1 remote merge/push/closeout through new ledger or claim such coverage. Both #109 enrolled execution and explicitly enrolled recovery are mandatory verifier-backed consumers; unenrolled compatibility behavior unchanged and marked outside guarantee. Deployment/key provisioning/real service mutation are separate cutover gates.
